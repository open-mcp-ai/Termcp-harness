# ADR-002：事件顺序、关联与完整性

- 状态：Proposed / 待 Core 确认
- 日期：2026-10-28
- 责任范围：Harness + Core 契约协作

## 背景
终端输出、marks、rail、审批和执行状态可能来自不同事件源。单连接传输保序不代表不同事件源具有统一的执行因果顺序。

## 需要回答
- 每种事件是否带 session ID、sequence、operation/correlation ID 和可信时间戳？
- 多个连接/通道之间如何比较顺序？
- 断连后能否按游标补拉？快照是否与事件流一致？
- marks/rail 如何关联终端输出范围？

## 暂定建议
Harness 保持各流内部顺序，按可信 ID 关联；仅按接收时间排列时标记为接收顺序。缺少关联字段时显示未知，不推断因果关系。重连后刷新快照；无补拉能力时说明历史可能不完整。

## 验证
模拟不同事件到达顺序、缺失 ID、重复事件、断连重连、旧异步结果晚到，以及跨会话隔离。

## 重新评估条件
Core 提供统一事件 envelope、序号/游标或操作关联能力。


## 快照与实时事件协调要求

在实现重连恢复前，需明确：快照是否具有版本/游标、快照期间到达的事件如何排序或合并、旧异步任务如何失效，以及无游标时能否补拉历史。Harness 不得仅凭本地接收时间或不可变状态结构宣称恢复完整。

实现策略不在本 ADR 中预先锁定。优先恢复必要会话状态，大体量终端历史可按需加载；是否使用批量事务、不可变数据结构或渐进式加载，应由正确性约束、当前框架与性能测量共同决定。
