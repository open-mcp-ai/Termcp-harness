# ADR-009：模块目录、自由组合与安装推荐

- 状态：Accepted / 模块清单、自由组合与推荐安装交互已确认；模块打包、签名、动态安装和安全实现仍待 PoC
- 日期：2026-10-28
- 责任范围：Harness Runtime、Terminal Workspace、扩展生态与发布体系
- 关联：`docs/product/VISION_v0.9.md`、`docs/architecture/DESIGN_v0.4.md`、`docs/architecture/UPSTREAM.md`、`docs/adr/ADR-008-desktop-technology-stack.md`、`docs/adr/ADR-011-mcp-native-agent-runtime.md`

## 1. 背景

产品方向是：Runtime 与 Terminal Workspace 稳定后，推出模块化组装。用户在安装 Harness 时可以选择需要的模块，安装后也可以调整模块配置，以实现更强的自定义化。

这个方向涉及三个不同问题，不能混在一起：

1. 安装包是否真的只包含用户选择的模块。
2. 运行时是否允许启用、停用或安装模块。
3. 第三方插件是否可以执行代码并访问 Harness 能力。

Wails + Go 会生成单一桌面二进制。仅靠配置隐藏功能，不会让最终二进制变小；真正的“按需安装”需要额外的打包、下载和隔离设计。

### 1.1 已确认的安装与组合原则

产品确认采用“模块目录 + 复选框推荐”，而不是固定产品档位：

- Harness Shell 是非模块基础，保证安装后至少有一个可展示、可恢复的工作台。
- 所有功能模块都出现在同一个模块清单中，前面使用复选框。
- 推荐模块根据使用场景预勾选，但用户必须可以取消任何推荐项。
- L0-L3 只表示模块的必要程度和适用场景，不是产品版本、权限等级或质量等级。
- 安装器和安装后的模块管理使用同一份模块目录和选择模型。
- 用户可以全选、全不选、搜索、按类型筛选、恢复推荐并保存自己的组合。
- 所有模块选择都可以由用户发起；硬依赖或安全冲突需要明确解释，软性的未验证组合可以继续安装并标记支持边界。

## 2. 产品目标

- 提供稳定的 Harness Shell，让用户在没有选择任何功能模块时仍能看到可恢复的工作台。
- 把所有功能模块放进同一个目录，按 L0-L3 和功能类型分组。
- 根据用户目标、运行环境和已检测组件给出可解释的推荐，而不是隐藏模块。
- 默认勾选推荐模块，但允许逐项取消，不把推荐变成强制套餐。
- 安装后可以继续添加、启用、停用、更新或卸载模块。
- 允许用户保存、导入、导出和分享自己的模块组合与 Workspace。
- 模块状态、权限、来源、版本、依赖和失败原因必须可见。
- 未被官方验证的组合可以存在，但必须明确标注支持边界。

## 3. 非目标

当前不承诺：

- 把 L0-L3 做成不可跨越的产品版本、权限或质量等级。
- 把推荐模块锁定为必选项，或禁用未勾选模块对应的复选框。
- 默认安装全部模块，或静默替用户选择。
- 首版 Terminal Workspace 立即支持任意模块动态加载。
- 用 Go `plugin` 作为跨平台模块机制。
- 允许第三方前端代码直接进入主界面并拥有全部桥接权限。
- 任意模块组合都获得同等级支持。
- 模块商城在模块生命周期和安全模型完成前上线。

## 4. Harness Shell 与功能模块

### 4.1 Harness Shell 不是功能模块

以下能力构成始终存在的展示底座，不出现在模块复选框中：

- 启动并展示一个 Harness 工作台。
- 模块目录、复选框、搜索、分类和组合保存。
- 布局、恢复入口和基础设置。
- 模块健康状态、缺失依赖和错误提示。
- 安全的“恢复推荐组合”和“仅保留 Shell”入口。

Shell 的最小保证是“可展示、可配置、可恢复”，不保证在没有任何执行模块时完成 Agent 或终端任务。

### 4.2 所有功能模块都可勾选和取消

以下能力可以是独立模块，也可以由多个模块共同提供：

- Agent Loop、Session 状态和工具调用状态。
- MCP 连接、工具能力状态和工具调用流水线。
- 终端输入、输出、顺序和会话状态。
- 连接、Core 定位和受管子进程生命周期。
- 审批呈现、拒绝/批准结果确认和结果未知状态。
- 凭据保护、日志脱敏和诊断。
- 工作流、自动化、插件、主题、通知和桌宠。

复选框不得因为“位于 L0”而灰掉。用户可以取消全部功能模块；此时 Shell 显示空工作台、缺失能力说明和恢复入口。

### 4.3 基础保证

任何组合至少保证：

- Shell 可以启动并展示当前模块状态。
- 缺失依赖、冲突和未验证组合有明确提示。
- 用户可以进入模块目录重新选择能力。
- 模块失败不会导致 Shell 无法恢复。

### 4.4 目录统一，生命周期不统一

统一模块目录只保证用户侧发现和选择一致，不意味着底层对象具有相同生命周期。

| 对象类型 | 示例 | 生命周期特征 |
|---|---|---|
| Runtime 内核组件 | Agent Loop、Session 状态机 | 有明确运行生命周期，但不一定独立安装 |
| 内建功能模块 | Terminal、Timeline、诊断面板 | 可随主程序构建，通过配置启停 |
| 外部服务连接器 | MCP Server 连接 | 独立发现、连接、授权和能力刷新 |
| 官方模块包 | 独立工具或功能包 | 下载、校验、安装、更新和卸载 |
| 第三方插件 | 社区扩展 | 独立隔离、权限、兼容和审计 |
| Workspace / Recipe | 面板布局、组合配置 | 只保存和恢复配置，不应获得执行权限 |

统一 Manifest 负责描述身份、类型、依赖、Capability、权限和状态；具体生命周期由对应适配器实现。

用户选择、安装、启用、运行和任务可用必须分别判断：

1. **安装关系**：模块是否被选择、是否可下载和安装。
2. **运行关系**：模块是否可启用、已启用、正在运行或失败。
3. **能力关系**：依赖、授权、模型、MCP 和外部服务是否足以完成当前任务。

所有复选框都可以操作，但“被勾选”只表示用户选择。硬依赖、版本不兼容或安全冲突可以阻止启用或执行，不能因为追求自由组合而把安全限制降级成普通提示。

## 5. 模块分类

### 5.1 按安装必要程度分组

这套 L0-L3 即“四级安装”，是安装页的分组标签，不是产品档位、权限等级或质量等级。

| 分组 | 含义 | 默认行为 | 示例 |
|---|---|---|---|
| **L0 · 基础能力** | Harness 核心运行和恢复常用能力 | 根据场景推荐，仍可取消 | Runtime Core、配置、诊断 |
| **L1 · 常用能力** | 大多数工作流会使用的模块 | 根据场景推荐，允许取消 | Terminal、Agent Timeline、审批 |
| **L2 · 专项能力** | 面向 MCP、开发、运维或自动化场景 | 默认较少勾选 | MCP Console、工具诊断、工作流 |
| **L3 · 扩展能力** | 桌面体验、实验能力和第三方模块 | 默认不勾选 | 桌宠、主题、社区插件 |

### 5.2 按功能类型分类

功能类型只用于目录筛选和检索：

- 终端与执行。
- Agent 与 Session。
- MCP 与工具。
- 审批与策略。
- 数据与诊断。
- 工作流与自动化。
- 展示与桌面体验。

### 5.3 按来源与信任分类

| 类型 | 来源 | 是否可执行代码 | 默认方向 |
|---|---|---|---|
| 内建功能模块 | Harness 官方 | 与主程序同构 | 可选择安装或启用 |
| 官方可选模块包 | Harness 官方 | 可能有独立进程 | 按需下载、校验和安装 |
| 第三方插件 | 外部开发者 | 是 | 独立隔离、授权后运行 |
| 目录条目 | 发布者/市场 | 取决于内容类型 | 只负责发现和分发 |

## 6. 候选方案

### 方案 A：内建模块 + 功能开关

- 所有第一方模块随主程序构建。
- 安装器和设置页通过配置启用/停用。
- 模块界面按配置注册。
- 不做任意代码动态加载。

优点：

- 与 Wails/Go 单二进制最兼容。
- 版本一致，测试和回滚简单。
- 可以快速验证模块化 UX 和用户需求。

限制：

- 不会显著减小安装包。
- 未启用代码仍在二进制中。
- 不能作为第三方插件执行模型。

建议作为第一阶段模块化验证方案。

### 方案 B：官方可选模块包

- 基础安装包含固定内核。
- 模块包独立版本、独立签名、独立下载。
- 前端资源按模块分包；后端能力使用受控进程或本地接口。
- 安装器记录组合，支持修复、更新和回滚。

优点：

- 可以真正减小初始安装体积。
- 模块边界更清晰。
- 适合官方维护的 MCP/插件/主题/桌面宠物模块。

限制：

- 需要发布、签名、兼容、下载和回滚体系。
- 测试矩阵增加。
- 独立进程会增加资源和生命周期复杂度。

只有在测量证明安装体积或模块隔离具有真实价值后再采用。

### 方案 C：第三方插件 SDK

- 插件运行在独立进程或沙箱中。
- 宿主通过版本化 RPC/IPC 暴露有限能力。
- 插件声明权限、资源上限和兼容版本。
- 默认不具备任意文件、命令、URL 或凭据访问。

这是长期目标，不应与官方内建模块共用“直接调用全部内部 API”的模型。

### 不推荐方案：Go `plugin`

不作为默认模块机制，原因包括：

- 对编译器、依赖和 ABI 版本高度敏感。
- 跨平台和交叉编译限制多。
- 模块崩溃可能影响主进程。
- 难以建立稳定的权限和生命周期边界。

如果未来需要 Go 扩展，应优先使用独立进程和版本化协议。

## 7. 模块 Manifest 最低字段

每个可安装模块至少声明：

- `id`、显示名称、描述。
- 模块版本与发布者。
- Harness 兼容范围。
- 支持平台与架构。
- 功能类型、L0-L3 安装分组和入口。
- 对象类型与生命周期适配器，例如内建模块、外部连接器、模块包、插件或 Workspace。
- `use_case_tags`：用于推荐场景匹配。
- `recommended` 或推荐规则，但不得表示强制安装。
- 安装体积、下载来源和离线可用性。
- 依赖模块与冲突模块。
- 提供的 Capability 和需要的 Capability。
- 所需权限和能力。
- 是否需要重启。
- 数据和配置目录。
- 卸载时保留/删除数据的策略。
- 签名、哈希和来源。
- 更新、撤销和回滚信息。

未确认或缺失的字段必须保守处理，不能默认获得权限。

## 8. 选择、安装、启用与能力状态

不得用一个“成功/失败”字段覆盖所有语义。至少分别记录：

### 8.1 选择关系

- **未选择**：用户没有勾选。
- **已选择**：用户希望安装或保留该模块，不代表已经安装。

### 8.2 安装关系

- **可发现**：出现在目录中，但尚未下载。
- **可安装**：Manifest、平台和来源信息完整。
- **已下载**：包已存在，尚未校验或安装。
- **已安装**：文件与元数据完整。
- **待更新 / 待卸载**：存在需要重启或迁移的操作。
- **安装失败**：校验、签名、下载或写入失败。
- **已撤销**：发布者或市场阻止继续使用。

### 8.3 运行关系

- **已停用**：不向当前工作流提供能力。
- **已启用**：能力已注册，但未必运行。
- **运行中**：独立进程或能力已启动。
- **运行失败**：启动或运行失败。

### 8.4 能力关系

- **能力就绪**：依赖、授权、模型、MCP 和目标服务满足当前任务。
- **能力受限**：部分依赖缺失或权限不足，只能完成受限任务。
- **能力未知**：尚无真实调用或健康证据。
- **不可用**：存在阻止当前任务的依赖、兼容或安全冲突。

每个状态必须基于真实证据，不以 UI 点击直接推断成功。不同对象类型可以省略不适用的阶段，但不能把缺失阶段当成通过。

## 9. 安装与运行时选择

### 9.1 安装页结构

安装页默认展示完整模块清单，推荐只影响预勾选状态和标记，不用来隐藏其他模块：

1. 顶部选择使用场景，例如终端协作、MCP 管理、Headless、完整工作台或自定义。
2. 系统根据场景、平台、已有 Core/Runtime 和模块依赖预勾选推荐项。
3. 所有功能模块默认都显示复选框；推荐模块可以被取消。
4. 用户可以全选、全不选、搜索、按 L0-L3 分组和按功能类型筛选。
5. 页面实时显示已选模块、下载体积、依赖、权限和需要配置的项目。
6. 提供“恢复推荐”“保存为我的组合”和“从文件导入组合”。

界面示意：

```text
安装 Harness

使用场景：[终端协作] [MCP 管理] [Headless] [完整工作台] [我自己选]

[ ] 只看推荐    [搜索模块]    [全部类型]

L0 基础能力
  [x] Runtime Core
  [x] 配置与诊断

L1 常用能力
  [x] Terminal
  [x] Agent Timeline
  [x] 审批面板

L2 专项能力
  [ ] MCP Console
  [ ] 工具调用诊断
  [ ] 工作流

L3 扩展能力
  [ ] 桌宠
  [ ] 主题
  [ ] 社区插件

已选 5 个模块 · 预计 82 MB
[恢复推荐] [全部取消] [安装]
```

Harness Shell 本身不出现在复选框中；它负责展示这个页面、恢复已安装模块并在全部功能模块被取消时提供重新选择入口。

### 9.2 推荐规则

- 推荐必须可解释，例如“你选择了终端协作，因此推荐 Terminal、Timeline 和 Approval”。
- 推荐不能隐藏模块，也不能把未推荐模块放进不可见区域。
- 第一版采用透明规则匹配，不依赖黑盒模型。
- 用户手动修改勾选后，不得因场景变化静默覆盖其选择；应提示可以恢复推荐。
- 推荐结果只是初始勾选，不是安装后的固定身份。

### 9.3 依赖与冲突

- 所有复选框保持可操作，不通过灰掉控件代替解释。
- 选择依赖模块 A 时，同时勾选依赖 B，并显示原因。
- 取消 B 时，提示 A 将不可用，并允许用户一并取消 A。
- 硬依赖缺失可以允许保留选择，但在依赖满足前不得启用或运行。
- 软依赖缺失允许安装和运行，但必须显示能力受限。
- 版本不兼容或安全冲突必须阻止受影响的启用或执行，并写明原因。
- 未验证组合可以安装和试用，但必须标记支持边界和恢复方式。

### 9.4 安装后

- 模块管理页复用安装页的目录、筛选、推荐和复选框模型。
- 已安装模块可以启用、停用、更新、卸载和查看数据策略。
- 新模块可以从扩展目录补装，无需重新选择整套产品版本。
- 用户可以保存当前模块组合为一个可分享的安装 Recipe。
- Workspace 布局和模块组合可以分别保存，也可以作为一个场景模板共同导出。

### 9.5 安装事务与记录

- 不设置不可取消的功能模块套餐。
- 安装失败时可以保留已完成部分并恢复选择。
- 记录实际安装清单、用户选择、推荐来源和未验证项。

### 9.6 运行时状态

- 启用/停用优先使用配置切换。
- 需要重启或独立进程的模块必须明确提示。
- 停用模块不等于删除数据。
- 卸载前说明凭据、缓存和会话数据的处理方式。
- 更新失败不得破坏当前可用版本。

## 10. 权限与安全

- 模块不能直接读取 Core 私有数据库或配置。
- 模块能力通过宿主代理和最小权限接口提供。
- 凭据默认不向模块暴露明文。
- 代码执行型模块默认独立进程或沙箱。
- 模块不能通过隐藏路由或前端脚本绕过审批。
- 市场可发现不等于已审计、已签名或可安全执行。
- 官方模块与第三方模块必须有不同的信任标签。
- 撤销、下架和签名失败必须让用户可见。

## 11. 支持矩阵与测试

不承诺任意组合都获得完整支持，也不把支持矩阵做成产品档位。至少定义：

- 官方验证的推荐组合，作为测试和示例基线。
- 允许安装但标记为未验证的组合。
- 因依赖或安全原因不能安装的组合。
- 全部功能模块取消时的 Shell-only 恢复场景。

必须覆盖：

- 推荐项全部取消、全选、全不选和恢复推荐。
- 用户手动选择被场景推荐覆盖或保留的规则。
- 选择模块自动勾选依赖、取消依赖时联动取消。
- 已选择、已安装、已启用、运行中和能力就绪不会互相冒充。
- 缺少硬依赖时保持选择，但不能启用或运行。
- 缺少软依赖时允许运行，并显示能力受限。
- 安全冲突或版本不兼容时明确阻止受影响操作。
- 模块缺失、损坏、版本不兼容。
- 依赖循环、冲突、重复 ID。
- 安装中断、下载失败、签名失败。
- 更新失败与回滚。
- 模块崩溃、重启和资源泄漏。
- 停用/卸载后的数据保留和迁移。
- 安装器与安装后模块管理显示同一份模块清单和状态。
- Shell 在所有功能模块不可用时仍可展示恢复入口。

## 12. 待确认问题

- 安装时选择是否必须改变最终二进制和安装包大小？
- 首批模块有哪些，哪些属于 L0-L3 的推荐候选？
- 模块是否必须支持在线补装，还是首版只提供离线模块包？
- 官方模块是否允许独立版本和独立发布节奏？
- 模块与第三方插件是否共用 Manifest 和生命周期模型？
- 模块权限如何映射到 Harness 和 Core 的公开能力？
- 是否接受模块独立进程带来的资源与启动成本？
- 官方推荐规则和验证组合由谁测试、认证和长期维护？
- 未验证组合的提示、支持和回滚边界如何定义？

## 13. 暂定建议

1. 先按“全部模块可见、推荐默认勾选、全部可取消”的交互做安装器和模块管理 PoC。
2. 用方案 A 验证配置型模块和推荐规则，再评估方案 B 的真实下载安装。
3. 收集安装体积、启动时间、取消推荐、补装模块和 Workspace 分享数据。
4. 第三方插件使用方案 C，不把 Go `plugin` 作为默认路径。
5. 在安全模型、签名、兼容和回滚完成前，不开放模块市场。
6. 模块化不得阻塞 Runtime、MCP 工具链和 Terminal Workspace 的核心可靠性。

本 ADR 记录方向，不代表上述能力已经实现。
