# ADR-007：契约基线、测试桩与兼容性验证

- 状态：Proposed / 双方确认前不得视为权威契约
- 日期：2026-10-28
- 责任范围：Harness + Core 契约协作

## 背景

Harness 需要可重复的 Mock 和契约测试，但若测试桩由 Harness 单方面依据推测维护，它可能只证明 Harness 与自身假设一致，而不能证明真实 Core 兼容。

## 暂定原则

1. Core 公开契约由 Core 侧权威来源负责；Harness 可维护版本化样例、适配层与测试场景。
2. 每项关键契约需标注来源、版本、确认状态和验证证据。
3. 先建立轻量级样例与测试桩，覆盖协议结构、错误响应、未知字段/枚举、断连与重复事件；不要求所有单元测试都依赖契约桩。
4. 契约变更时先判断兼容性并更新权威定义/样例，再运行相关测试；不得只改 Mock 使测试通过。
5. 契约测试失败是“不一致信号”，不自动等于 Core 缺陷；需区分真实契约变更、桩过期、Harness 适配错误和行为语义未定义。
6. Schema 只验证结构的一部分。审批原子性、事件因果顺序、超时后的执行结果、快照一致性等行为语义需文档约定与真实 Core 集成测试验证。

## 待确认

- Core 是否已有版本化 OpenAPI、JSON Schema 或协议定义？
- 哪个团队/负责人维护权威契约，如何通知兼容性变更？
- 是否有稳定的 Core 测试实例、版本矩阵和 CI 接入方式？
- 对暂未确认的字段与行为，Harness 使用什么明确的临时假设与退出条件？

## 验收标准

- 测试桩与真实 Core 权威契约的来源和差异可追踪。
- 至少一组关键 API/事件样例能被自动化测试消费。
- 测试失败可区分 schema/fixture 变化与行为回归，且不会通过无依据地放宽断言来消除失败。
- 尚未由真实 Core 验证的能力明确标为未验证。
