# docs/governance/AGENTS_v0.3.md — Termcp Harness 开发代理规则

> 状态：历史规则归档。正文保留 v0.3 时期的内容；当前执行规则以根目录 `AGENTS.md` 为准，产品与架构引用指向现行规范。
>
> 适用对象：参与 Harness 代码、测试、文档和审查的 AI 编码 Agent。
> 本文件约束代理行为；它不能替代测试、代码审查、CI 或 Core 服务端安全控制。

## 1. 开始任务前

1. 阅读 `docs/product/VISION_v0.9.md`、`docs/architecture/DESIGN_v0.4.md`、相关 ADR、`docs/ux/UX-RECOVERY.md` 和当前实现文档。
2. 检查当前代码、已有测试、Core 公开 API/WS 契约；不得只依据设计文档推断当前实现。
3. 明确任务属于 Harness、Core 或双方协作。若需要 Core 新能力，先提出契约需求，不得在 Harness 内复制 Core 内部逻辑作为捷径。
4. 将关键陈述标记为：已由代码/测试确认、来自公开契约、团队确认、推断、未知。
5. 优先最小变更；不为尚未决定恢复的 Web、插件市场或远期需求提前搭建通用框架。

## 2. 不可违反的边界

- 不 import Core 内部包或直接读写 Core 私有数据库/配置来绕过公开契约。
- 不复制终端执行引擎、Agent 规划逻辑、服务端审批规则或 Core 权限策略。
- 不把 UI 按钮、本地锁、前端状态或客户端校验描述为服务端安全保证。
- 不把“点击拒绝”直接显示为“已拒绝”；必须依据可信服务端确认。
- 请求超时、断连或响应丢失时，不得把有副作用操作视为失败后无条件重试。
- 不把接收时间当作真实执行顺序；不以时间接近或文本相似建立确定的操作—输出因果关系。
- 不重排终端字节；可以合并渲染批次，但不得改变字节顺序或混合会话。
- 不丢弃审批、会话关闭、执行状态等关键控制事件作为普通日志处理。
- 不引入无界队列、无界缓存或随输出量不断累积的 UI 状态。
- 不在不能确认所有权时终止进程、删除目录或清理数据。
- 不让多个受管 Core 实例共用同一数据目录，除非 Core 已明确支持且有验证证据。
- 不将 Token、Authorization 头、私钥或敏感终端内容写入普通日志/诊断包。
- 不未经用户/项目负责人授权 commit、push 或执行破坏性数据操作。

## 3. 人工与 Agent 并发操作

- 将连接状态、Shell/执行状态、审批状态、输入来源和本地 UI 状态分开建模。
- 不假定 Agent 正在运行时输入是独占的；不假定审批等待会暂停 Shell 中全部进程。
- 对可见冲突提供明确提示；只有 Core 公开契约确实支持时，才调用暂停、取消、互斥或抢占能力。
- 对拒绝、关闭、取消、超时分别建模，不将它们合并成一个“停止”状态。
- 如果操作结果未知，提示用户核对权威状态；不自动重复提交有副作用操作。

## 4. 事件、顺序和 UI 状态

- 按连接/会话隔离事件流；清理已关闭会话的监听器、队列和异步任务。
- 对异步结果使用序号、版本校验或取消机制，防止旧结果覆盖新状态。
- 不把 WebSocket/TCP 传输顺序问题与不同事件源缺少共同顺序语义混为一谈。
- 有序终端流只允许分块或合并渲染，不允许重排。
- 如果协议没有 sequence/operation/correlation ID，只能呈现可证明的关系；其余显示未知或未关联。
- 重连后先刷新权威快照；无游标/补拉能力时，不宣称历史事件完整。
- 关键控制事件与普通输出分开处理；若任何事件会被丢弃，必须显式报告并证明不会静默丢失控制状态。

## 5. Core 进程与数据目录

- 只管理本 Harness 实例明确拥有的子进程。
- 不通过端口号直接 kill 进程，不自动终止未知 Core。
- 启动前核对实例身份、端口和数据目录；遇到冲突优先停止启动并报告。
- 连接外部 Core 与管理本地子进程是不同权限，不能混用生命周期操作。
- Core 多进程共享目录、SQLite 并发、锁和迁移语义均需以 Core 公开说明/代码/测试确认，不可猜测。

## 6. 安全与凭据

- 不把不可信终端输出作为 HTML/脚本执行。
- 不新增任意 URL、任意文件读写或任意命令执行的通用桥接 API，除非经过明确安全审查。
- 认证信息通过最小必要路径传递，避免写入 URL、普通日志、前端持久化存储或诊断包。
- 诊断导出默认排除完整终端历史、环境变量、秘密字段和敏感参数；执行脱敏并要求用户确认。
- 任何“安全”声明需明确依赖的 Core 服务端能力与测试证据。

## 7. 测试要求

按风险选择测试；涉及以下区域时必须覆盖相关场景：
- 输入并发、审批拒绝/超时、请求结果未知。
- WS 断连/重连、快照刷新、事件关联缺失、旧异步任务。
- 高输出、超长行、多字节文本、窗口 resize、切换会话与退出。
- 子进程启动/关闭、意外退出、实例冲突、外部 Core 所有权。
- 凭据脱敏、诊断包内容、错误状态显示。
- 公开契约字段缺失、未知枚举、错误响应和版本差异。

不能运行测试时，说明原因和未验证风险；不得声称通过。不得为让测试变绿而无理由删除断言或放宽安全行为。

## 8. 契约测试与快照恢复

- 不把 Harness 自维护的 Mock/schema 当成 Core 权威契约；每项关键契约需记录来源、版本和确认状态。
- 契约测试失败时先分类：Core 真实变更、Mock/schema 过期、Harness 适配缺陷或行为语义未定义；不得直接改桩让测试变绿。
- 不要求所有单元测试机械依赖契约桩；外部协议、序列化、桥接与状态恢复测试应使用版本化样例。
- JSON Schema/OpenAPI 不能替代对审批原子性、事件因果顺序、超时后执行状态等行为语义的验证。
- 设计重连恢复时，先说明快照权威性、快照期间实时事件如何协调、旧任务如何失效，以及缺少游标/版本时的限制。
- 不预设必须使用不可变数据结构或一次性统一提交；根据正确性需求、数据规模和性能测量选择实现。
- 优先按需加载大体量历史数据；测量内存峰值、恢复耗时、UI 响应与丢失/重复事件，再决定是否增加复杂机制。

## 9. 用户侧异常提示

- 对执行结果未知、审批状态未知、人工/Agent 输入冲突、Core 断连、历史不完整和数据目录冲突等高风险场景，提示必须说明可确认事实、未知项和下一步安全行动。
- 不武断归因故障原因；不把请求已发送说成已执行；不把 UI 拒绝动作说成服务端已阻止执行。
- 只在有证据时使用“未发送”“明确失败”等状态；其余使用“未能确认/结果未知”等准确表述。
- 当前先覆盖关键恢复场景，不为文案字典、国际化或通用通知框架过度设计。

## 10. 文档和变更汇报

- 架构/状态/契约/安全边界变更：更新 `docs/architecture/DESIGN_v0.4.md` 与相关 ADR。
- 产品方向/范围变化：才更新 `docs/product/VISION_v0.9.md`。
- 当前实现、运行方式、测试命令、平台支持状态变化：更新 README。
- 标清“已实现”“已验证”“计划中”“待 Core 确认”。
- 完成后汇报：变更、依据、测试命令与真实结果、未验证项、Core 协作项和风险。
