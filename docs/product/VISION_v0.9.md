## 0. 一句话定位

**Termcp Harness 是 MCP 原生的 Agent Runtime 与人机共享的终端工作台：统一管理 Agent 执行、MCP 工具、上下文、会话、策略、轨迹和恢复，并让人类在同一执行现场观察、审批和接管。**

更短地说：

> **一个开放的、MCP 原生的、人机共用的终端 Agent 运行时。**

Harness 的边界：

- 不是第二个 Core。
- 不是固定策略、固定模型或固定规划范式的单一自主 Agent 产品；它可以承载和协调 Agent。
- 不复制 Core 的 SSH、PTY、Shell、审批执行或权限链路。
- 不被某个桌面 UI、模型厂商、插件框架或部署方式锁定。
- 终端工作台是第一方体验层，不是运行时本体。

## 1. 为什么需要 Harness

MCP 已经让模型能够发现和调用外部工具，但 MCP 本身不负责：

- Agent 的多轮执行循环。
- 上下文、记忆、会话与恢复。
- 工具调用前后的策略、审批和验证。
- 多 MCP Server 的能力发现、权限和生命周期。
- 工具失败、超时、取消、结果未知和重试。
- 人类如何在同一执行现场观察和接管。
- 如何以 headless、容器或远程方式部署。
- 如何把模型、工具、UI 和部署边界解耦。

因此，MCP 解决“能调用什么”，Harness 解决“何时调用、是否允许、如何执行、结果是否可信、失败后怎么办”。

> **MCP 提供能力，Harness 提供秩序、信任和恢复。**

围绕终端的真实问题包括：

1. **工具碎片化。** Agent 需要多个 MCP 服务，但发现、连接、授权、能力和健康状态分散。
2. **执行不透明。** 模型调用、工具参数、审批、终端输出和最终影响难以形成可理解的操作链。
3. **状态不诚实。** 超时、断连和进程退出经常被误报为失败；有副作用的操作可能被盲目重试。
4. **人机割裂。** Agent 在一条通道中工作，人却只能通过日志或另一套终端界面理解结果。
5. **部署不开放。** 产品可能开源，但运行时、插件、UI 和部署方式仍被内部实现绑定。
6. **扩展不可信。** MCP、插件、商城和桌宠等扩展缺少清晰的权限、生命周期与失败隔离。

Harness 的价值不是“再做一个终端”或“再做一个聊天 Agent”，而是让 Agent 的终端工作变得可治理、可观察、可干预和可恢复。

## 2. 目标用户与核心任务

优先服务：

- **AI 辅助终端使用者：** 希望 Agent 完成终端任务，同时能看懂并随时接管。
- **Agent 与工具开发者：** 需要调试 MCP 工具、Agent 循环、策略和失败恢复。
- **多环境操作者：** 需要在本地、远程或容器化环境中运行同一套 Harness。
- **MCP 生态参与者：** 希望任何 MCP Server、Agent 或 UI 都能通过稳定契约接入。
- **异常场景中的普通用户：** 需要看得懂结果未知、审批未确认、连接中断和历史不完整。

核心任务按优先级排列：

1. 启动或连接 Harness Runtime。
2. 连接 Agent/模型与 MCP 工具。
3. 在策略和审批下执行工具调用。
4. 在终端工作台观察、干预和接管同一执行现场。
5. 追踪操作来源、上下文、结果和影响。
6. 在超时、断连或失败后确认状态并安全恢复。
7. 以 headless、容器、桌面或其他 UI 形式开放部署和接入。

## 3. 产品原则

### 3.1 MCP 原生，而不是 MCP 兼容列表

MCP 是 Harness 的一等边界：

- Core 是一个 MCP Server。
- Harness 作为 MCP Client/Host 管理和调用 MCP 工具。
- 外部 MCP Server 可以按统一状态模型被发现、登记、连接、读取能力、启用、停用和受管。
- 第三方工具不应被迫依赖 Harness 私有插件 API 才能工作。

### 3.2 终端是共享执行现场

终端工作台不是装饰面板，也不是 Agent 日志查看器。它是人与 Agent 共同工作的执行现场：

- 同一 Session/Shell 中的人机输入和输出可被理解。
- 工具调用、审批、输出和异常可以定位到相关上下文。
- 人可以在不伪造“暂停 Agent”保证的前提下干预或接管。
- Agent 可以读取人类已有上下文，但不能据此假定拥有跨客户端互斥。

### 3.3 来源和状态必须诚实

Harness 只能基于可信来源实际提供的数据建立关联：

- 可以证明的来源，明确显示。
- 无法证明的来源，显示为未知或未关联。
- 不把时间接近、文本相似或本地接收顺序当作真实因果关系。
- 不把“工具调用已发送”说成“工具已执行”。
- 不把“点击拒绝”说成“服务端已阻止执行”。
- 未取得执行证据时，不显示“成功”。

### 3.4 稳定内核，开放边缘

Harness 不采用“一切皆插件”的产品原则。以下能力属于稳定内核：

- Agent Loop 与运行时生命周期。
- MCP 连接、工具注册和能力状态。
- 工具调用流水线。
- 策略、审批和凭据边界。
- Session、上下文与事件日志。
- 取消、超时、重试和恢复。
- 基础控制 API 与事件流。

模型、MCP Server、工具、UI、存储、部署、主题和桌宠属于可替换边缘。

### 3.5 Headless 优先，UI 可选

运行时必须能够脱离图形界面工作：

- CLI、daemon、容器或服务模式可以启动 Harness。
- 第一方终端工作台通过稳定控制契约附着。
- 关闭 UI 不等于停止 Agent、工具调用或会话。
- UI 不是安全保证，也不是唯一控制入口。

### 3.6 恢复优先于盲目重试

- 有副作用的操作在结果未知时不得自动重试。
- 重试必须说明幂等依据、次数、退避和用户可见结果。
- 工具调用需要区分提交、接受、执行、成功、失败、取消、过期和未知。
- 恢复时以 Core、MCP Server 和 Harness 权威状态为准，不用本地猜测填补缺失。

### 3.7 开放不等于无边界

真正的外部开放至少包括：

- 部署开放：CLI、daemon、容器和远程运行不依赖某一种 UI。
- 接入开放：MCP、HTTP、WebSocket、CLI/SDK 使用版本化公开契约。
- 工具开放：任意符合 MCP 的服务可以接入。
- 模型开放：不绑定单一模型厂商或 API 兼容层。
- 扩展开放：插件与适配器有稳定 Manifest、权限和生命周期。
- 状态开放：Session、事件和调用轨迹可以导出与审计。

开放性不意味着任意代码、任意网络、任意文件权限或任意 UI 都能无约束进入主进程。

## 4. 产品能力模型

Harness 由三层产品面与两类长期扩展组成。

### 4.1 A · Runtime Kernel（核心）

- Agent 循环与会话生命周期。
- 模型适配器与会话上下文。
- MCP Client/Host 与能力发现。
- 工具调用前的策略、审批和参数约束。
- 工具执行、结果观察和调用后的验证。
- 事件日志、操作轨迹和来源标记。
- 超时、取消、断连、结果未知和恢复。
- 基础控制 API、事件流和诊断。

### 4.2 B · MCP 控制面

- 本地/远程 MCP Server 注册。
- 已发现、已登记、已连接、能力已读取、已启用、已停用、不可用和受管状态。
- 工具名称冲突、版本兼容和健康检查。
- 按 Agent、Session、任务或工作区限制工具。
- 凭据引用、环境变量、工作目录和网络边界。
- 调用日志、失败诊断和连接恢复。

MCP 控制面是 Harness 的核心能力，不等同于商城。

### 4.3 C · Terminal Workspace（第一方体验层）

- 终端、Shell、Session 与运行时状态。
- Agent 操作、工具调用、审批、输出和异常的统一时间线。
- 在终端上下文中查看策略、审批和结果。
- 人工接管、上下文注入、继续和停止。
- 断连、恢复和结果未知提示。
- MCP 能力与工具状态面板。

终端工作台不是通用 SSH 管理器的复制品。连接、文件、转发、多窗格和标签应在真实需求与差异化验证后逐项引入。

### 4.4 D · 扩展与生态（长期方向）

- 展示型插件、主题、通知和桌宠。
- 自动化、定时任务和可复用工作流。
- MCP/插件目录与商城。
- 第三方工具与 UI SDK。
- 团队策略、多 Agent、多 Core 和远程控制面。

这些能力不能削弱运行时内核、审批、凭据保护和恢复语义。

### 4.5 E · 模块目录、安装与发布

模块化不是把 Harness 做成固定几档产品，而是提供一个可自由拼装的模块目录：

- **固定 Shell：** Harness Shell 始终提供工作台展示、模块目录、布局、恢复和基础设置。
- **全部模块可见：** 所有功能模块都出现在同一份目录中，前面使用复选框。
- **推荐可取消：** 根据使用场景预勾选推荐模块，但用户可以取消任何推荐项。
- **L0-L3 分组（四级安装）：** L0-L3 只表示必要程度和适用场景，不是产品版本、权限等级或质量等级。
- **自由组合：** 用户可以选择、取消、搜索、筛选、全选、全不选和恢复推荐。
- **安装后继续扩展：** 安装器和模块管理使用同一目录，后续可以补装、启用、停用、更新和卸载。
- **组合可分享：** 当前模块组合与 Workspace 可以保存、导入和导出。
- **真实模块化：** 区分配置隐藏和真正裁剪安装包，不能把功能开关冒充安装时组合。

如果用户取消全部功能模块，Harness Shell 仍然可展示空工作台、缺失能力说明和恢复入口。官方提供经过验证的推荐组合，但不阻止用户安装未验证组合；支持边界必须明确可见。

统一目录不等于统一生命周期。Runtime 内核、内建功能、MCP 连接器、模块包、第三方插件和 Workspace Recipe 可以共用发现与选择体验，但底层分别使用适合自己的生命周期。用户选择、安装、启用、运行和能力就绪必须分别显示；复选框只代表选择。

模块化交互的详细决策见 `docs/adr/ADR-009-modular-composition.md`。

## 5. 当前范围与优先级

### 5.1 当前交付策略

**先完成开放运行时边界和最小人机共享终端闭环，再扩展生态。**

- Web UI 仍暂停新增开发，见 `docs/product/WEB-DEFERRED.md`。
- 不为未来商城或 Web 预建通用框架。
- 第一方 Terminal Workspace 是当前主要体验入口，但不得成为 Runtime 的唯一入口。
- Desktop 仍是重要参考实现，不是 Harness 的架构基线。

### 5.2 当前阶段范围

P0 · Runtime 与契约：

- 确定 Harness Runtime 的 headless 启动、控制 API、事件模型和部署边界。
- 核对 Core 的 MCP、HTTP、WebSocket、审批、实例和恢复契约。
- 定义 MCP 状态机、工具调用状态机、Session 和操作轨迹。
- 建立可重复测试入口和契约快照机制。

P1 · 最小 Agent 闭环：

- 一个 Harness Runtime 实例。
- 一个 Agent Session。
- 连接 Termcp Core MCP，至少再验证一个外部 MCP Server 或等价工具来源。
- 工具调用前策略、人工审批和调用后结果记录。
- 明确区分成功、失败、取消、超时和结果未知。
- 有界上下文、事件日志和安全恢复。

P2 · Terminal Workspace：

- 一个终端视图与一个 Agent Session 关联。
- 人机共享同一 Shell 上下文。
- 工具调用、审批、输出和恢复提示在同一界面可见。
- 人工接管和继续。
- 基础 MCP 状态面板。

暂不默认承诺：

- 完整 SSH 管理器。
- 多窗格、复杂布局和全套文件/转发能力。
- MCP/插件商城。
- 任意代码插件运行时。
- 桌宠和完整桌面体验。
- 远程团队控制面、多 Agent/多 Core 编排。
- 完整录制、复杂凭据保险库或企业审计平台。

## 6. 首个完整工作流

首个完整版本聚焦一条端到端链路：

> 启动 Headless Harness → 连接 Termcp Core 与工具来源 → 创建 Agent Session → 打开关联终端工作台 → Agent 发起工具调用 → 策略/人工审批 → 观察执行和输出 → 记录成功、失败或未知 → 必要时人工接管或安全恢复。

至少满足：

1. Harness Runtime 在没有 Terminal Workspace 时也能启动并接受控制。
2. MCP 工具来源、连接和真实能力状态可理解。
3. Agent 的工具调用经过明确策略，审批结果不超前于服务端确认。
4. 终端工作台和 Agent 指向同一可验证的 Session/Shell。
5. 工具调用、终端输出和审批之间只展示可证明的关联。
6. 超时或断连后不自动重试有副作用的操作。
7. 第三方 Agent/UI 可通过稳定契约接入，而不依赖内部插件树。
8. 高频终端输出下关键控制事件仍可见、顺序不乱、内存有界。

这是一组产品级验收要求，不是当前实现完成度声明。

## 7. Core、Harness 与 Terminal Workspace 的责任边界

| 领域 | Core | Harness Runtime | Terminal Workspace |
|---|---|---|---|
| 执行 | SSH、PTY、Shell、文件、转发和真实会话状态 | 不复制执行引擎；通过公开契约调用 | 不持有执行引擎 |
| Agent | 不承担 Agent 循环或模型上下文 | 运行/协调 Agent、工具循环和会话 | 展示和干预 |
| MCP | 暴露 Core 自身 MCP Server | 作为 MCP Client/Host 管理多个工具来源 | 展示能力与状态 |
| 策略 | 执行服务端权限与已有审批约束 | 在调用前/后执行 Harness 策略和验证 | 展示策略、提交审批、确认结果 |
| 数据 | Core 权威会话/终端数据 | Harness 自有 Session、操作轨迹与配置 | UI 临时状态和视图状态 |
| 进程 | Core 自身进程与服务 | 管理自身 Runtime 与明确拥有的子进程 | 不拥有 Runtime |
| 扩展 | 只暴露其公开能力 | 注册、连接、授权、生命周期与诊断 | 展示与交互 |

需要双方或团队确认的事项：

- Agent Runtime 的正式边界、Agent 与外部宿主的关系。
- MCP 工具调用与 Core 事件的稳定关联字段。
- 人工与 Agent 并发输入、审批原子性和结果未知语义。
- Core 的启动、实例身份、健康检查和数据目录契约。
- Terminal Workspace 是直连 Core 终端流，还是经 Harness 控制面转发。
- Harness 自身公开控制 API、事件流和插件契约。

Harness 文档不能单方面规定 Core 内部实现，也不能把 Core 未承诺的接口当成既有事实。

## 8. 技术方向与技术栈

### 8.1 已确认方向

- 第一方 Terminal Workspace：Wails v2 + Go + React/TypeScript/Vite + `@xterm/xterm`。
- Runtime 与 UI 分离，Runtime 必须支持 headless 运行。
- 通过公开 HTTP、WebSocket、MCP、CLI/API 等契约连接 Core 和外部工具。
- 不 import Core 内部包，不复制 Core 执行引擎。
- 终端字节流保序，有界缓冲，关键控制事件可见。
- MCP 工具描述、Schema 和返回值均按不可信输入处理。
- 代码执行型插件需要独立隔离、权限和信任模型。

### 8.2 尚未确认

- Runtime 的具体语言、进程模型、打包和部署形态。
- MCP SDK/实现、事件模型、控制 API 和持久化格式。
- Terminal Workspace 的终端数据路径及远程部署方式。
- 首个模型适配与有界 Agent Loop 已落地为 OpenAI-compatible 非流式切片；真实 provider 兼容、流式输出、摘要和跨重启上下文仍未确认。
- 插件 Manifest、RPC/SDK、签名、沙箱和商城技术。
- 正式平台、发布矩阵、更新和回滚方案。
- 测试框架、性能阈值和契约快照格式。

Go 与 Wails 生态是当前优先方向，但 Runtime 不应因为 UI 选择 Wails 而被绑定为桌面进程。实际技术命令以 manifest、README 和真实测试为准。

## 9. 路线图

### 阶段 0：产品与契约确认

- 确认 ADR-011 的三平面架构和开放边界。
- 核对 Core 的 MCP、HTTP、WebSocket、审批和实例契约。
- 定义 Harness 控制 API、事件流、MCP 状态和工具调用状态。
- 建立测试入口、契约快照和威胁模型。

**退出条件：** Runtime 与 Workspace 边界、外部协议、部署方式、未决契约和降级方案明确。

### 阶段 1：Headless Runtime 最小闭环

- 启动 Runtime 并暴露基础控制 API/事件流。
- 连接 Termcp Core MCP。
- 实现最小 Agent Loop、工具调用流水线和策略接口。
- 记录 Session、工具调用、审批和结果状态。
- 实现超时、取消、断连、结果未知和安全恢复。

**退出条件：** 无 UI 时可完成一条真实工具调用；状态和失败有测试证据；有副作用操作不会盲目重试。

### 阶段 2：MCP 控制面

- 注册、连接和检查多个 MCP Server。
- 展示能力、版本、健康、权限和生命周期状态。
- 处理工具冲突、断连、重连和能力变化。
- 按 Session/Agent 授权工具。
- 验证第三方 MCP 不依赖 Harness 私有 SDK。

**退出条件：** 至少一个非 Core MCP 可通过公开 MCP 契约接入并安全执行；状态可诊断。

### 阶段 3：Terminal Workspace

- 终端与 Agent Session 绑定。
- 工具调用、审批和输出时间线。
- 人工接管、继续和安全恢复。
- MCP 状态面板。
- 高频输出和会话切换性能基线。

**退出条件：** 人与 Agent 共享同一执行现场；关联边界诚实；相对 Core Web UI 和 Desktop 的价值可复现。

### 阶段 4：开放部署与插件边界

- Headless、CLI、daemon、容器或远程部署 PoC。
- 版本化控制 API、SDK 和插件 Manifest。
- 展示型插件与能力型插件隔离。
- 配置、Session 和事件导出。
- 模块目录、L0-L3 分组、推荐规则和自由复选安装 PoC。
- 安装器与安装后模块管理共用同一清单。

**退出条件：** 第三方 UI/Agent/工具可在不了解 Harness 内部实现的情况下接入；模块推荐可取消；安装后可以补装模块；部署和恢复可验证。

### 阶段 5：生态与桌面扩展

- MCP/插件目录与商城。
- 模块化安装与运行时启停。
- 模块组合、Workspace 和安装 Recipe 的导入导出与分享。
- 桌宠、通知、主题和多窗口。
- 多 Agent、多 Core 与团队能力评估。

**退出条件：** 供应链、权限、撤销和回滚有真实安全模型；扩展不削弱核心运行时。

## 10. 产品质量与成功标准

优先看真实任务是否更容易完成、系统是否更可信，而不是功能数量：

- Runtime 能否在无 UI 情况下完成真实 Agent 任务。
- 任意 MCP Server 是否能通过公开契约接入，而不依赖内部插件树。
- 人工和 Agent 能否理解自己正在操作同一 Session/Shell。
- 工具调用、审批和输出的关联是否有可信证据。
- 超时、断连和失败后能否区分已知状态与结果未知。
- 有副作用操作是否避免无依据重试。
- 高频终端输出下控制事件是否仍可见、顺序是否保持。
- 推荐模块是否容易理解、可以全部取消并在需要时恢复。
- 用户能否在安装后自由补装模块而不被固定产品档位限制。
- 新增扩展是否显著增加复杂度、权限面或维护负担。
- 部署、状态导出和版本兼容是否开放且可验证。

每个阶段必须有可重复验证的退出条件。Vision 定义结果；具体测试和性能阈值放入 Design、测试计划或 CI。

仅能编译、启动或展示页面不等于正式支持。未测试平台和能力必须明确标注。

## 11. 当前决策、假设与待确认事项

### 11.1 当前决策

- Harness 重新定位为 MCP 原生 Agent Runtime 与人机共享的终端工作台。
- Harness Runtime 与 Terminal Workspace 分层；Runtime 必须可 headless 运行。
- Terminal Workspace 是第一方体验层，不是唯一入口。
- MCP 控制面是核心能力，不只展示连接配置。
- 稳定内核、开放边缘；不采用“一切皆插件”。
- 所有功能模块使用同一复选框清单；推荐项默认勾选但可以取消。
- L0-L3 是安装分组，不是产品档位、权限或质量等级。
- Harness Shell 是固定展示底座；全部功能模块取消时仍提供恢复入口。
- 安装器和安装后的模块管理复用同一目录与组合模型。
- 目录统一但生命周期不统一；选择、安装、启用、运行和能力就绪必须分开表示。
- Core 仍是终端执行和会话事实的权威来源。
- 第一方终端 UI 技术栈采用 Wails v2 + Go + React/TypeScript/Vite + `@xterm/xterm`。
- Web UI 暂停新增开发。
- 未经人工同意不 commit/push。

### 11.2 待验证假设

- Harness 作为独立 Runtime 能在不复制 Core 的前提下提供真实 Agent 执行价值。
- 现有 Core 公开契约足以支持可信的人机共享终端和工具调用关联。
- 外部 MCP Server 的能力、健康和生命周期可以在不依赖私有 SDK 的情况下统一管理。
- Headless Runtime + 可选 UI 的架构能比单体桌面产品提供更好的部署开放性。
- 稳定内核/开放边缘能在不无限扩大测试矩阵的前提下支持扩展。
- 全部模块可见、推荐项默认勾选且可取消的安装方式，能同时降低新用户门槛并保留高级自由度。
- 用户愿意为“可观察、可干预、可恢复”而不是功能数量选择 Harness。

### 11.3 待确认事项

- Harness Runtime 的首版语言、进程模型、启动和控制协议。
- Agent Loop 是否由 Harness 内置、由外部 Agent 提供，还是两者都支持。
- Terminal Workspace 直连 Core 终端流，还是经 Harness 代理。
- Core 的 MCP 工具、事件、审批、实例和恢复契约。
- MCP 工具调用的统一幂等、取消、重试和结果未知语义。
- 第三方 Agent/UI 接入 Harness 的公开 API/SDK。
- 插件与模块的 Manifest、隔离和发布模型。
- 首个发布平台和 headless 部署目标。
- Web 是否恢复，以及恢复时与 Terminal Workspace 的关系。

## 12. 明确非目标

除非用户或项目负责人明确批准，Harness 不：

- 重写 Termcp Core 的 SSH、PTY、Shell、文件、转发或审批执行能力。
- 成为第二个 Core。
- 变成只服务一个固定模型、一个固定厂商或一种固定规划范式的封闭 Agent。
- 复制 Termcp-Desktop 的完整 SSH 管理器和所有终端功能。
- 把“一切皆插件”作为稳定内核的设计目标。
- 把 L0-L3 做成不可跨越的产品版本或权限等级。
- 把推荐模块锁定为不可取消的强制套餐。
- 隐藏未推荐模块，或用灰掉复选框代替依赖与冲突说明。
- 为了统一目录而强迫 Runtime 内核、MCP 连接器、模块包、插件和 Workspace 使用同一种生命周期。
- 首版建设完整插件市场、MCP 市场、模块市场或团队协作平台。
- 把 UI 审批描述为服务端安全保证。
- 在未知结果下自动重复有副作用的操作。
- 通过隐藏入口、插件或前端脚本绕过权限、审批和审计。
- 因未来 Web 或商城需求提前搭建通用框架。

## 13. Web 的当前处理

Web UI 不在当前产品开发主线中：

- Headless Runtime 和开放 HTTP/WebSocket 契约仍然重要。
- Web UI 暂停新增功能，保留为设计与实现参考。
- 当前不为 Web 预建跨端通用框架。
- 将来是否恢复、如何与 Terminal Workspace 共享语义，见 `docs/product/WEB-DEFERRED.md`。

---

## 本版核心结论

**Termcp Harness 不是第二个 Desktop，也不是通用办公 Agent。它是 MCP 原生的 Agent Runtime 与终端工作台：让人和 Agent 在同一个执行现场协作，并让工具、模型、会话、策略、轨迹和恢复过程可观察、可干预、可部署。**

**MCP 提供能力，Harness 提供执行秩序、信任边界和恢复能力。稳定内核必须可靠，开放边缘必须真正可替换。**
